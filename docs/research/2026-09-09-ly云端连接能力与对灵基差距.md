# ly 云端连接能力 & 对灵基的差距 —— 调研

> 日期:2026-09-09 | 方法:本地源码实证 + 本机环境实测 + 仓库既有调研文档
> 回答两个问题:① `ly` 能不能连云端环境并实际操作?② 和金蝶官方灵基差多少?

---

## 0. 一页纸结论

1. **代码层没有任何地址限制** —— `ly` 的 URL 就是 `env.url + path`,无白名单、无域名校验、无 localhost 限制。
   "能不能连云端"是**配置问题,不是能力问题**。
2. **但认证只实现了苍穹一套** —— 只有 `getToken / verifyToken / withdrawToken`。能否连上云端,
   取决于该云端是不是苍穹技术栈:
   - **星空旗舰版 / AI 套件 / 私有云订阅苍穹(苍穹栈)** → 现有流程大概率可用,**近零适配**;
   - **星空公有云 K3 Cloud(.NET / kdsvc 栈)** → 需要 `LoginBySign` 签名登录,代码里**零命中,现在登不上**。
3. **当前本机只配了一个 `local-cosmic`**(`http://127.0.0.1:8080/ierp`),2026-09-09 实测 `ly doctor` 六项全绿、
   `ly meta biz-apps` 与 `ly data precheck` 均返回真实数据 —— **能连、能操作**。
4. **和灵基的差距要分两层看**:比"企业 AI 操作系统"差一个产品品类(不该追);
   只比"让 AI 改 ERP 的手艺",缺口是可枚举的三个工程项(v0.4 K3 Cloud 分支、v0.5 扩展表单与插件注册、无 UI/治理),
   其中前两项约 60% 可复用。**真正无法靠写代码消除的差距是官方身份**(SLA、接口稳定性、本体层)。

## A. 云端连接能力

### A1. 无地址限制(可指向任意 URL)

| 事实 | 证据 |
|---|---|
| 请求 URL = `env["url"] + path`,`url` 完全取自配置 | `src/ly/auth.py:51`、`src/ly/api.py:47` |
| 全仓 `src/` 检索 `localhost\|白名单\|域名\|startswith` 只命中 `cli.py:387`,那是校验 `ly api` 的 *path 参数* 而非 *环境 URL* | `grep -rni` 全仓扫描 |
| CLI 帮助里 `--url` 示例虽写 `http://127.0.0.1:8080/ierp`,但仅为示例,非约束 | `src/ly/cli.py:460` |

### A2. 认证只有苍穹一套(这是真正的边界)

| 事实 | 证据 |
|---|---|
| 只实现 `/kapi/oauth2/getToken`、`/kapi/oauth2/verifyToken`、`/kapi/oauth2/withdrawToken` | `src/ly/auth.py:111,129,141` |
| 全仓 `src/` 检索 `LoginBySign\|k3cloud\|galaxy\|星空\|公有云` **零命中** | 全仓扫描 |
| 可选字段 `acgw`(`x-acgw-identity` 头)与 `datacenter` 都是苍穹概念,不是为 K3 Cloud 准备的 | `src/ly/config.py:69-70`、`src/ly/api.py:23-24` |
| 报文 style 仅 `kapi` / `legacy` 两种,均为苍穹体系 | `src/ly/api.py:21-35` |
| 设计器会话通道(`session.py`)走 `auth/queryParameters.do` → `getPublicKey.do` → `yzjlogin.do`,也是苍穹系 | `src/ly/session.py:126-145` |

### A3. "星空"必须分家(既有调研的结论)

| 事实 | 证据 |
|---|---|
| 星空公有云 = K3 Cloud(.NET / kdsvc);星空旗舰版 / AI 套件 = 苍穹技术栈,与 ly 同构 | `docs/research/2026-09-07-xingkong-cloud-diff.md:12` |
| K3 Cloud **没有** getToken,需 `LoginBySign` 签名登录拿 `KDSVCSessionId` 有状态会话 | 同上:13-14 |
| WebAPI 形状完全不同:K3 Cloud 是 `...DynamicFormService.Save.common.kdsvc` + `{"parameters":[...]}` 位置参数;苍穹是 `/kapi/...` + `errorCode` 信封。现有 `_is_body_401` 假设在 K3 Cloud 失效 | 同上:14 |
| 复用度评估:config/envelope/HTTP/缓存约 **60% 可复用**,auth 与报文必须各写一套 → 属**分支逻辑**,非薄适配层 | 同上:15,143 |
| 遗留待验证(需真实环境):KDSVCSessionId 有效期、公有云网络白名单/限流、`parameters` 兼容下限、产品线确认 | 同上:164-169 |
| 路线图 v0.4 星空适配仍为 `[ ]`(未做);v0.5 扩展表单全流程亦未做 | `README.md:152-153` |

## B. 与灵基的差距

### B1. 先划清"不可比"的部分

灵基 = 金蝶官方**企业 AI 操作系统**(组织级底座,六层架构,对话/工作/开发三模式 + 治理可信 + 市场生态,
原生融合星瀚/星空/星辰,按点数席位计费)。Lingya = 个人**跨 harness 开发工具集**。
二者不在同一层级 —— 拿来做全量对比,等价于问"git 和 GitLab 差多少"。以下只比**"让 AI 改金蝶 ERP"这一件共同的事**。

### B2. 同一件事上的真实差距

| 维度 | Lingya 现状 | 灵基 | 差距性质 |
|---|---|---|---|
| 环境覆盖 | 苍穹 ✓(实测);旗舰版/套件 大概率 ✓;**K3 Cloud ✗** | 原生融合星瀚/星空/星辰 | **差 1 个产品线** = v0.4 |
| 元数据二开 | build-meta / modify-meta / 操作与校验全生命周期 ✓ | 内置 app-build 等技能 | 基本持平 |
| 业务数据 | precheck/publish/save/query/operate ✓(2026-09-07 实测) | 智能体直接建单据跑审批 | 基本持平 |
| 转换规则(BOTP) | list/get/detail/enable/disable ✓(2026-09-09 实测,设计器会话通道) | 走官方能力 | Lingya 有独门路径(OpenAPI 通道绕开"其他开发商发布"锁定) |
| 扩展表单全流程 | ✗(v0.5 未做) | 有 | **差 1 项** |
| 插件开发(Java 编译+注册) | ✗(CONTEXT 明载"不在首跑范围") | 有 | **差 1 项** |
| UI / 低代码编排 | 无,纯 CLI | 客户端 + 可视化编排 | 设计取舍,不补 |
| 治理 / 权限 / 审计 | 无(仅写操作门 + 本地红线) | 企业级,过信通院检验 | 设计取舍,不补 |
| 组织协同 / Skill 市场 / 生态 | 无 | 有 | 设计取舍,不补 |
| 模型通道 | **自带任意 OpenAI 兼容渠道** | 官方调度 | **Lingya 更自由** |
| 成本 | **零点数** | 点数/席位 | **Lingya 更优** |
| 官方知识检索 | `kd` 匿名四类源 ✓ | 内置 RAG + 33 年本体层 | 各有胜负:kd 零点数但逆向无承诺;灵基有 SLA 但收费 |

### B3. 诚实的三个答案

1. **比"企业 AI 操作系统"**:差一个产品品类的距离,**永远不该去追** —— 那是组织级命题,不是个人 CLI 该解的。
2. **只比"AI 改 ERP 的手艺"**:主要缺口是三个可枚举工程项 ——
   - ① K3 Cloud 分支(v0.4,约 60% 复用,需真实环境验证 4 项遗留);
   - ② 扩展表单全流程 + 插件注册(v0.5 / 插件开发里程碑);
   - ③ 无 UI、无治理 —— **设计取舍,主动不补**。
3. **真正无法靠写代码消除的差距:官方身份。**
   灵基握有官方接口契约、业务本体层与 SLA;`kd` 走的是**非官方逆向接口**(README 明载"官方升级可能导致失效"),
   `ly` 用的是公开 OpenAPI(官方一改契约就断)。这是结构性差距,不是工程量问题。
