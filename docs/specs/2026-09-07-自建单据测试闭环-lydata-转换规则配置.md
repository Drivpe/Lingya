# Spec：自建单据测试闭环 + ly data 业务通道 + BOTP 转换规则配置

> 产出自 2026-09-07 grilling 会话；调研依据见 `docs/research-lingya-转换规则与自建单据调研.md`。
> 三阶段：A 元数据层测试闭环 → B `ly data` 业务数据通道（即路线图 v0.3）→ C BOTP 转换规则配置。

## Problem Statement

（用户/agent 视角）当前用 `ly` 已能新建和修改自建单据的元数据，但有三处断点：

1. 建完/改完只能靠临时会话手工读回校验，没有一条可重复的「建单据→改字段→读回验证」闭环路径。
2. 单据建好后无法通过 API 写入真实业务数据并走 保存→提交→审核，无法证明这张单据在系统层面真的能用。
3. 单据转换（BOTP）规则只能进设计器【单据转换管理】页面手工配置，agent 既看不到现有规则、也无法配置新规则，跨单据流转的自动化断在最后一环。

## Solution

给 `ly` CLI 按三个工作块补齐能力，全部以子命令 + JSON 信封暴露，`skills/ly/SKILL.md` 同步更新：

- **A · 元数据层自建单据测试闭环**：用现有 `ly meta build-meta / modify-meta` + 只读端点，形成标准化的「建→改→读回断言」验证流程。
- **B · `ly data` 业务数据通道**：开放平台初始化 + 逐对象发布操作 API，提供对自建单据的保存/提交/审核命令，实现业务层端到端。
- **C · BOTP 转换规则配置**：逆向设计器【单据转换管理】页面内部接口，封装为 `ly convert-rule` 子命令，先只读（列规则/读详情）后写入（新建/修改，走写操作门），最终以一次真实下推完成验收。

## User Stories

1. As an agent, I want a 标准化的「build-meta 建单据 → modify-meta 改字段 → 只读端点读回断言」操作序列, so that 我能自建单据并自动确认结构与预期一致。
2. As an agent, I want 元数据写失败时拿到结构化的 error 信封（type/code/message/hint）, so that 我能不依赖人工解读地定位与重试。
3. As an agent, I want `ly data` 能对指定自建单据执行 save, so that 我能把真实业务数据写入单据。
4. As an agent, I want `ly data` 能执行 submit 与 audit, so that 我能走完单据生命周期并验证单据真实可用。
5. As an agent, I want 业务操作调用前由工具自动完成开放平台初始化与操作 API 发布的前置检查, so that 我不必手工管理发布状态。
6. As an agent, I want `ly convert-rule list`, so that 我能列出环境里已预置与自建的转换规则。
7. As an agent, I want `ly convert-rule get`, so that 我能读出某条规则的完整配置（源单、目标单、字段映射、值转换）。
8. As an agent, I want `ly convert-rule` 的新建/修改默认只返回请求预览、加确认参数才执行, so that 配置错误不会污染环境。
9. As an agent, I want 通过 API 对源单执行下推, so that 我能验证配置的转换规则真实可跑。
10. As a developer, I want 三个工作块全部只通过 `ly` 子命令使用, so that 我在任意 harness（灵基/ZCode/opencode）里的体验一致。
11. As a developer, I want SKILL.md 随新命令同步更新, so that 任何 agent 宿主都能即刻发现并正确调用新能力。
12. As a developer, I want 写操作门、JSON 信封契约、纯标准库零依赖等既有约束不被破坏, so that 项目设计哲学保持连贯。
13. As a developer, I want 首条验证链路从环境已预置的规则中现选（标准单→标准单）, so that 验收建立在真实可复现的数据上。
14. As a maintainer, I want 实施前先核对本地与 GitHub 远程的提交差异, so that 推送文档更新时不会覆盖远程历史。

## Implementation Decisions

- **前台形态 = CLI 子命令 + SKILL.md 更新**，不做 Web UI（与 ADR 0001「CLI 核心 + 薄 SKILL 包装」一致）。
- **三阶段顺序固定为 A → B → C**（测试先行）；C 的端到端下推验收依赖 B 的业务操作发布路由。
- **BOTP 路线 = 逆向设计器内部接口**。已查证（kd 裸检索，2026-09-07）：苍穹无 ConvertRule OpenAPI，单据转换仅有设计器入口与 Java 插件（IBOSConvertRule/ConvertRuleMeta）两条既有路径；动手前先对设计器页面抓包 + 对 devportal ai-meta 族探针实测双重确认。
- **convert-rule 先只读后写**：第一步列/读（零风险摸清接口数据结构），第二步新建/修改，写请求走现有 `write_gate()`（confirm 预览 / `--confirm` / free）。
- **下推执行**：作为业务操作经 B 阶段的对象操作发布路由调用，不单开通道。
- **环境事实**：唯一环境 `local-cosmic`（苍穹本地轻量环境），账号为管理员，BOS 扩展应用权限无障碍；已知元数据写坑（Lock 属性、updateOperation 全量替换、`<key>.id` 引用、IsCheckAllEntity 反义等）须在实现中规避。
- **硬约束**：Python 纯标准库零第三方依赖；输出严格 JSON 信封；MSYS 路径还原逻辑覆盖所有新端点透传；凭证只存 `~/.kd/config.json`，任何日志/文档不落密钥。

## Testing Decisions

- **唯一测试缝 = `ly` CLI 的 JSON 信封输出**（用户已确认）：所有验证只断言命令的外部行为（信封 `ok/data/error`）与环境读回状态，不打内部函数，不新增缝。
- **好测试标准**：只测外部可见行为——命令输出与系统读回状态；不测实现细节、不 mock 服务端。
- **覆盖模块**：A 验证 `ly meta` 建/改/读闭环；B 验证 `ly data` 保存/提交/审核；C 验证 convert-rule 读→写→下推。
- **Prior art**：`ly doctor` 的一站式体检模式、agent 端到端读回校验（CONTEXT.md 记载的验收方式）；姊妹仓 kingdee-knowledge-kit 的 verify 回归脚本模式可作参考，但不引入其独立仓结构。
- 每工作块验收 = agent 在 local-cosmic 上真实跑通对应用户故事并逐条断言。

## Out of Scope

- 任何 Web UI / 浏览器配置界面。
- 星空公有云 K3 Cloud 适配（v0.4 分支：LoginBySign 会话体系）。
- Java BOTP 插件（IBOSConvertRule）开发路线。
- 标准表单扩展应用全流程自动化（v0.5）。
- kingdee-knowledge-kit（kd）侧的任何改动。
